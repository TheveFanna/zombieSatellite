# Requirements Document

## Introduction

zombieSatellite is a mobile-first web app for the Kiroween 2026 hackathon (category Resurrection). Users pick a real "zombie satellite" from a fixed catalog of 7 satellites. The app predicts passes over the user's location from public TLE data (SGP4), guides the phone toward the satellite in AR during a pass, plays a simulated beacon whose pitch follows the Doppler shift, and issues a digital QSL card after the pass. The app is pure software: only the public orbital data is real, and the app receives no real radio-frequency signals.

This spec, orbit-engine, covers two deliverables:

1. The project scaffold: a Next.js 16 + React 19 + TypeScript (strict) project that builds and runs tests. It has no UI beyond what the framework template needs. The PWA is a later spec. The package manager of the project is pnpm, chosen by the project owner on 2026-11-15 instead of npm; the source code of the Orbit_Engine does not depend on this choice.
2. The Orbit_Engine: a framework-independent TypeScript library under `src/lib/orbit` that fetches and parses TLEs from CelesTrak, propagates with satellite.js 6.0.2 (SGP4), computes look angles and slant-range rate, and predicts passes with refined boundaries and peaks.

### Normative sources

- Sections 2 (conventions C01–C88, formulas 2.9.x) and 4 (numeric baselines) of the Reference_Document are normative for this spec, except where this list supersedes them.
- Section 3 items apply only where named. This spec names P10 (TLE lookup by NORAD ID must request the TLE format and return exactly one record) as normative. It cites P16 (1-minute pass sampling underestimates the peak of ISS pass 2 by 3.19°, section 4.7) as the error that the Pass_Predictor must not inherit.
- C25 states that only the position is used and the velocity is not. Requirement 8 supersedes C25: the Range_Rate uses the SGP4 velocity vector.
- C77 (1-minute pass boundaries, no interpolation) and C78 (maximum elevation taken from discrete samples) are superseded by Requirement 10. The 60 s grid survives only as the Coarse_Scan.
- C79 (pass duration (end − start) / 60 000 ms, displayed rounded to whole minutes) is kept as the derived pass duration of Requirement 9, criterion 4, without the display rounding.
- C80 (minimum elevation fixed at 0°) is superseded by Requirement 9: Min_Elevation is a caller parameter whose default is 0°.
- Formula 2.9.8 is refined by Requirements 10 to 12. Requirement 12 refines every Coarse_Scan_Maximum at or below Min_Elevation. The truncation semantics of formula 2.9.8 at window edges are kept; the Start_Truncated and End_Truncated flags are the only addition.
- C17 states that the TLE checksum is not validated. Whether the TLE_Parser also verifies the modulo-10 checksum is a design decision. All four Baseline_TLE_Snapshot lines carry correct checksums (ISS line 1 = 0, line 2 = 5; 59705 line 1 = 4, line 2 = 6). Rejecting non-TLE bodies does not rely on checksums (Requirement 4).
- C86 (cache and TLE auto-update thresholds) belongs to the removed satellite-library feature and does not apply. The TLE_Cache TTL follows Requirement 5.
- Section 4.1 tolerances apply where this document does not set a stricter one: azimuth and elevation ±0.01°, slant range ±0.1 km, altitude ±0.1 km. The pass-time tolerance of ±1 min (4.1, 4.10) is replaced by ±10 s.

### Out of scope

- Any UI beyond the scaffold's root layout and placeholder page; AR, Three.js scene coordinates, device orientation and HUD guidance (C40–C76, 2.9.3–2.9.6, baselines 4.4 and 4.5). The later AR spec uses the project pass-lock tolerance of ±10°, not the reference value of 8°.
- Beacon audio and Doppler synthesis, the session state machine, QSL cards, the PWA.
- The data of the 7-satellite catalog. This spec defines no catalog entries.
- Satellite search, a user satellite library, a custom backend API, server-side caching, persistent storage (IndexedDB, localStorage).
- The English translation of the Reference_Document (a pre-submission item).

### Known limitations

1. A dip of the Elevation to or below Min_Elevation that lasts less than 60 s between two adjacent Coarse_Scan samples above Min_Elevation is not detected, so the Pass_Predictor reports one Pass across the dip. No such dip occurs in the baseline windows of Requirements 11 and 13 (verified 2026-11-14).
2. The 1 s steps of the Brute_Force_Reference can understate the peak elevation of an ISS pass through the zenith by up to about 0.5°, because the ISS Elevation near the zenith changes by about 1° per second. Requirement 10, criterion 7 is therefore verified on the Requirement 13 windows (Requirement 13, criterion 6).
3. Look_Angles and Range_Rate for an Observer position that coincides with the satellite position (Slant_Range 0 km) are unspecified, because Observers are assumed to be near the Earth's surface.

## Glossary

- **Project_Scaffold**: The Next.js 16 + React 19 + TypeScript project skeleton delivered by this spec, including package.json, pnpm-lock.yaml, TypeScript and Vitest configuration, the root layout and one placeholder root page.
- **Orbit_Engine**: The framework-independent TypeScript library delivered by this spec, located under `src/lib/orbit`. It consists of the TLE_Fetcher, TLE_Parser, TLE_Cache, Propagator and Pass_Predictor.
- **TLE_Fetcher**: The Orbit_Engine component that obtains a TLE_Record for a NORAD catalog number, from the TLE_Cache or from the CelesTrak_GP_Endpoint.
- **TLE_Parser**: The Orbit_Engine component that validates TLE_Text and converts TLE_Text into a TLE_Record.
- **TLE_Cache**: The in-memory store of TLE_Records that the TLE_Fetcher uses, keyed by NORAD catalog number.
- **Propagator**: The Orbit_Engine component that computes ECI_Position, ECI_Velocity, ECF_Position, GMST, Look_Angles and Range_Rate for a Satrec at a UTC_Instant.
- **Pass_Predictor**: The Orbit_Engine component that finds the Passes of a satellite over an Observer within a Search_Window.
- **Public_Interface**: The functions (including methods of exported classes and objects), constants and types that the Orbit_Engine exports for use by code outside `src/lib/orbit`. The design names the entry modules that export them.
- **Engine_Source_Module**: A module that implements the TLE_Fetcher, TLE_Parser, TLE_Cache, Propagator, Pass_Predictor or the Public_Interface, or a module of this repository that such a module imports directly or indirectly. Test_Suite files, and fixtures and helpers that only the Test_Suite uses, are not Engine_Source_Modules.
- **Test_Suite**: The Vitest test files of this spec, including unit, baseline and property-based tests.
- **Reference_Document**: `docs/reference/TECHNICAL_ROUTE.md` in this repository, the trimmed technical route of the author's earlier personal project SatAware AR.
- **CelesTrak_GP_Endpoint**: The CelesTrak general perturbations query service at `https://celestrak.org/NORAD/elements/gp.php`.
- **Fetch_Function**: A function with the signature of the WHATWG `fetch` API that the TLE_Fetcher uses to send HTTP requests. A caller can supply one, for example a mock in tests.
- **TLE_Text**: A text given to the TLE_Parser, normally the three-line body (object name line, TLE line 1 and TLE line 2) that the CelesTrak_GP_Endpoint returns with FORMAT=tle. A TLE_Text may be invalid. The TLE_Parser accepts a TLE_Text when the TLE_Parser returns a TLE_Record for that TLE_Text, and rejects the TLE_Text when the TLE_Parser reports an Engine_Error for that TLE_Text.
- **TLE_Record**: The parsed result of one TLE_Text that the TLE_Parser accepts. The record holds the object name, the raw line 1 and line 2, the section 4.2 fields NORAD_CAT_ID, OBJECT_ID, EPOCH, MEAN_MOTION, ECCENTRICITY, INCLINATION, RA_OF_ASC_NODE, ARG_OF_PERICENTER and MEAN_ANOMALY, the semi-major axis and the altitude. Where a Public_Interface function takes a TLE_Record as input, a value counts as a TLE_Record when the value has the TLE_Record fields with the types that the design fixes, including the raw line 1 and line 2 as strings. A value without that structure gives an Engine_Error of category invalid-input (Requirement 2, criterion 11). A structurally valid TLE_Record whose line 1 and line 2 make satellite.js 6.0.2 `twoline2satrec` return a Satrec with a non-zero error code gives an Engine_Error of category invalid-tle (Requirement 6, criterion 10; Requirement 9, criterion 15).
- **Satrec**: The SGP4 satellite record that satellite.js 6.0.2 `twoline2satrec` builds from TLE line 1 and line 2.
- **Baseline_TLE_Snapshot**: One of the two TLEs printed in Reference_Document section 4.2: ISS (ZARYA), NORAD 25544, and ZHIHUI TIANWANG-1 01A, NORAD 59705.
- **Reference_Observer**: The observer of Reference_Document section 4.1: latitude 39.9042° N, longitude 116.4074° E, altitude 0 km.
- **UTC_Instant**: A point in time given as a JavaScript `Date` or as milliseconds since 1970-01-01T00:00:00Z, interpreted in UTC (C01).
- **Observer**: A geodetic observer position: latitude in degrees, WGS84 geodetic, north positive, range −90 to +90 (C26); longitude in degrees, east positive, range −180 to +180 (C27); altitude in kilometres above the WGS84 ellipsoid, up positive (C28).
- **ECI_Position**: The satellite position in the TEME frame output by SGP4, in kilometres (C20, C21).
- **ECI_Velocity**: The satellite velocity in the TEME frame output by SGP4, in kilometres per second (C20, C21). Requirement 8 uses it as the SGP4 TEME velocity v_teme.
- **ECF_Position**: The satellite position in the Earth-centred Earth-fixed frame, in kilometres (C23).
- **GMST**: Greenwich mean sidereal time, the angle from the TEME equinox direction to the Greenwich meridian, in radians in [0, 2π), computed from UTC (C05, C22).
- **Look_Angles**: The Azimuth, Elevation and Slant_Range of a satellite as seen by an Observer.
- **Azimuth**: The angle from true north to the satellite's horizontal direction, clockwise positive: 0° north, 90° east, 180° south, 270° west, in the half-open interval [0°, 360°) (C37).
- **Elevation**: The angle of the satellite above the Observer's local horizontal plane, in degrees in [−90°, +90°], up positive, without refraction correction (C36).
- **Slant_Range**: The straight-line distance from the Observer to the satellite, in kilometres (C35).
- **Range_Rate**: The time derivative of the Slant_Range, in kilometres per second; negative while the satellite approaches the Observer, positive while the satellite recedes.
- **Earth_Rotation_Rate**: ω⊕ = 7.292115 × 10⁻⁵ rad/s about the ECF +Z axis.
- **Search_Window**: The closed UTC interval [window start, window start + window duration] in which the Pass_Predictor looks for Passes.
- **Min_Elevation**: The elevation threshold of a pass search, in degrees. The satellite counts as above the threshold only when Elevation is strictly greater than Min_Elevation (C38 generalised).
- **Pass**: A maximal time interval inside the Search_Window during which the Elevation is greater than Min_Elevation. A Pass has a Rise_Instant, a Set_Instant, a Peak_Instant, a Maximum_Elevation, a duration in minutes (Requirement 9, criterion 4), a Start_Truncated flag and an End_Truncated flag. Known limitation 1 of the Introduction describes a case in which a reported Pass spans a short interval at or below Min_Elevation.
- **Rise_Instant**: The start of a Pass: the instant at which the Elevation increases through Min_Elevation, or the window start when the Pass is start-truncated.
- **Set_Instant**: The end of a Pass: the instant at which the Elevation decreases through Min_Elevation, or the window end when the Pass is end-truncated.
- **Peak_Instant**: The instant inside both the Pass and the Search_Window at which the Elevation is greatest.
- **Maximum_Elevation**: The Elevation at the Peak_Instant.
- **Start_Truncated**: A Pass flag that is true when the satellite is already above Min_Elevation at the window start, so the Rise_Instant is clipped to the window start. The design fixes the field name.
- **End_Truncated**: A Pass flag that is true when the satellite is still above Min_Elevation at the window end, so the Set_Instant is clipped to the window end. The design fixes the field name.
- **Coarse_Scan**: The evaluation of Elevation at 60 s steps from the window start to the window end, which locates candidate Passes before refinement.
- **Coarse_Scan_Maximum**: A Coarse_Scan sample whose Elevation is greater than the Elevation of the preceding Coarse_Scan sample and greater than or equal to the Elevation of the following Coarse_Scan sample. The first sample needs only the second condition, and the last sample only the first. A sample with a propagation-failure result is never a Coarse_Scan_Maximum; when a neighbouring sample is tested, a propagation-failure sample counts as lower than every Elevation.
- **Brute_Force_Reference**: An in-test ground truth that test code computes at run time, without calling the Pass_Predictor, by evaluating Elevation with the Propagator over a time interval: at the interval start, at every 1 s step after the interval start that lies before the interval end, and at the interval end.
- **Brute_Force_Pass**: A maximal run of consecutive Brute_Force_Reference samples whose Elevation is greater than Min_Elevation. A sample with a propagation-failure result counts as not above Min_Elevation. Its rise is the first sample of the run, its set is the first sample after the run (none when the run ends at the interval end), and its peak elevation is the highest Elevation in the run. A Pass overlaps a Brute_Force_Pass when at least one sample of that Brute_Force_Pass lies in the closed interval [Rise_Instant, Set_Instant] of the Pass. The Brute_Force_Pass of a Pass is the Brute_Force_Pass that the Pass overlaps.
- **Engine_Error**: An error reported by the Orbit_Engine that carries one machine-readable category and a human-readable message. The categories are invalid-input, network, http, invalid-tle and catalog-mismatch. The design fixes the identifiers and the representation.
- **TTL**: The time-to-live of a TLE_Cache entry, measured from the instant the fetch of that entry completed.
- **Entry_Age**: The age of a TLE_Cache entry at the instant a caller requests the entry's NORAD catalog number, in milliseconds: the Cache_Clock reading at that caller request minus the Cache_Clock reading at the instant the HTTP request that produced the entry ended in a TLE_Record. Serving the entry from the TLE_Cache does not reset the Entry_Age.
- **Cache_Clock**: The clock source from which the TLE_Fetcher reads the current time as a UTC_Instant to compute Entry_Age. The design fixes the clock source.
- **In_Flight_Request**: An HTTP request to the CelesTrak_GP_Endpoint for a NORAD catalog number N that the TLE_Fetcher has started and that has not yet ended in a TLE_Record or an Engine_Error. It counts as started at the instant of the caller request that causes it, before the TLE_Fetcher calls the Fetch_Function.
- **Request_Timeout**: The fixed time in milliseconds after which the TLE_Fetcher aborts an unfinished request. The design fixes the value.
- **Mock_CelesTrak_Fetch**: A test Fetch_Function that answers HTTP 200 with content type text/plain and the ISS Baseline_TLE_Snapshot as the body, with the name line right-padded with trailing spaces and CRLF line endings, as CelesTrak formats responses.
- **Live_Test_Variable**: The environment variable that enables the Live_Test while the variable holds a non-empty value (Requirement 14, criteria 3 and 4). The design fixes the variable name.
- **Live_Test**: The opt-in test that requests NORAD 25544 from the real CelesTrak_GP_Endpoint.

### Requirement 2: Framework-independent engine boundary, units and time

**User Story:** As the zombieSatellite developer, I want the orbit engine as a plain TypeScript library without React, Next.js or DOM dependencies, using UTC and fixed units, so that the same code runs in Node tests and in the browser and gives the same numbers in every time zone.

#### Acceptance Criteria

1. THE Orbit_Engine SHALL place every Engine_Source_Module in `src/lib/orbit` or a subdirectory of `src/lib/orbit`.
2. THE Orbit_Engine SHALL limit the imports of every Engine_Source_Module, counting static imports, type-only imports, re-exports and dynamic `import()` expressions, to the package specifier `satellite.js` without a subpath and to modules under `src/lib/orbit`, so that no Engine_Source_Module imports React, Next.js, a Node.js built-in module such as `node:fs`, or any other package.
3. WHILE the host is a Node.js 22 process without DOM globals, that is, with `window`, `document`, `navigator`, `localStorage` and `indexedDB` undefined (Node.js 22 defines `navigator` by default, so the test environment removes it), THE Orbit_Engine SHALL run every Public_Interface function to completion, meaning that each call returns, or settles its returned promise, without any error other than an Engine_Error that Requirements 2 to 13 specify for its inputs, with a supplied Fetch_Function such as the Mock_CelesTrak_Fetch wherever the function sends HTTP requests.
4. THE Orbit_Engine SHALL accept every point in time that a Public_Interface function takes as input, such as the UTC_Instant of a Propagator call and the window start of the Pass_Predictor, both as a JavaScript `Date` and as a number of milliseconds since 1970-01-01T00:00:00Z, with exactly equal results for a `Date` and the number equal to its time value.
5. WHILE the host time zone is a zone other than UTC, THE Orbit_Engine SHALL return, for the same inputs with every point in time given by the same time value, outputs identical to the outputs produced with the host time zone set to UTC: the same structure, every number exactly equal, every returned point in time with the same time value, every string equal, and every Engine_Error with the same category and message.
6. THE Orbit_Engine SHALL use these units at the Public_Interface: degrees for angles other than GMST, including the Observer latitude and longitude, Azimuth, Elevation, Min_Elevation, Maximum_Elevation, INCLINATION, RA_OF_ASC_NODE, ARG_OF_PERICENTER and MEAN_ANOMALY; radians for GMST; revolutions per day for MEAN_MOTION, revolutions per day² for MEAN_MOTION_DOT and revolutions per day³ for MEAN_MOTION_DDOT (C13, C14); inverse Earth radii for BSTAR (C15); kilometres for positions and distances, including the Observer altitude, the Slant_Range and the semi-major axis and altitude of the TLE_Record; kilometres per second for velocities and Range_Rate; hours for the window duration (C81); and milliseconds for the TTL (C04).
7. IF a Public_Interface function fails for a reason other than an SGP4 propagation error, for which the Propagator returns a propagation-failure result (Requirement 6, criterion 5), THEN THE Orbit_Engine SHALL report the failure as an Engine_Error with exactly one of the categories invalid-input, network, http, invalid-tle and catalog-mismatch, namely the category that Requirements 2 to 9 assign to that failure.
8. THE Orbit_Engine SHALL return every point in time in a Public_Interface result, such as EPOCH, Rise_Instant, Set_Instant and Peak_Instant, as a UTC_Instant, with all such results in the same form: either all JavaScript `Date` values or all numbers of milliseconds since 1970-01-01T00:00:00Z.
9. IF a point in time given to a Public_Interface function is an Invalid Date (a `Date` whose time value is NaN), a number that is NaN, infinite or outside the ECMAScript Date range of −8.64 × 10¹⁵ to +8.64 × 10¹⁵ ms, or a value of any other type, such as an ISO 8601 string, THEN THE Orbit_Engine SHALL report an Engine_Error of category invalid-input.
10. THE Orbit_Engine SHALL keep every Engine_Source_Module free of references, as identifiers or as properties of `globalThis`, to the DOM globals `window`, `document`, `navigator`, `localStorage` and `indexedDB` and to the Node.js-specific globals `process`, `Buffer`, `global`, `require`, `module`, `exports`, `__dirname`, `__filename`, `setImmediate` and `clearImmediate`, so that the same code runs in browsers and in Node.js 22.
11. IF a Public_Interface function receives, where it requires a Satrec, a TLE_Record or an Observer, a value that is not one, THEN THE Orbit_Engine SHALL report an Engine_Error of category invalid-input.

### Requirement 3: TLE retrieval from CelesTrak by NORAD catalog number (P10)

**User Story:** As the zombieSatellite developer, I want to fetch one satellite's TLE from CelesTrak by NORAD catalog number directly from the client, so that the app needs no custom backend and the reference project's ID-lookup defect (P10, JSON requested but TLE parsed) cannot return.

#### Acceptance Criteria

1. WHILE no In_Flight_Request for NORAD catalog number N exists, WHEN a caller requests N, N is an integer from 1 to 99999, and the TLE_Cache holds no entry for N whose Entry_Age is less than the TTL, THE TLE_Fetcher SHALL send exactly one HTTP GET request, with no retry, using the request URL `https://celestrak.org/NORAD/elements/gp.php?CATNR=N&FORMAT=tle` exactly, where N is written as a decimal integer without leading zeros (N = 5 gives `CATNR=5`).
2. THE TLE_Fetcher SHALL include exactly one FORMAT query parameter, with the value `tle`, in every request URL.
3. THE TLE_Fetcher SHALL set no request headers on any request, so that browsers send the cross-origin GET request without a CORS preflight request.
4. WHERE the caller supplies a Fetch_Function, THE TLE_Fetcher SHALL send every request through the supplied Fetch_Function.
5. WHERE the caller supplies no Fetch_Function, THE TLE_Fetcher SHALL send every request through the global `fetch` as it is defined when the request is sent, so that the Test_Suite can replace the global `fetch` after the Orbit_Engine is imported (Requirement 14, criterion 2).
6. WHEN the Fetch_Function resolves with a response of HTTP status 200 whose body text the TLE_Parser accepts and the NORAD_CAT_ID of the resulting TLE_Record equals the requested NORAD catalog number, THE TLE_Fetcher SHALL return exactly one TLE_Record, equal in every field to the TLE_Record that the TLE_Parser returns for that body text.
7. IF the requested NORAD catalog number is not a value of type number that is an integer from 1 to 99999 inclusive, the range of the five-digit TLE field of C18, THEN THE TLE_Fetcher SHALL report an Engine_Error of category invalid-input without calling the Fetch_Function (for example for 0, 100000, 25544.5, NaN or the string `"25544"`).
8. IF the call to the Fetch_Function throws or returns a rejected promise, THEN THE TLE_Fetcher SHALL report an Engine_Error of category network that carries the thrown value or the rejection reason as the cause.
9. IF the Fetch_Function resolves with a response whose HTTP status is not 200, including status 403 for rate limiting, THEN THE TLE_Fetcher SHALL report an Engine_Error of category http that carries the HTTP status code, regardless of the response body.
10. IF the Fetch_Function resolves with a response of HTTP status 200 whose body text the TLE_Parser rejects, such as `No GP data found`, an empty body or the JSON body `[]`, THEN THE TLE_Fetcher SHALL report an Engine_Error of category invalid-tle.
11. IF the Fetch_Function resolves with a response of HTTP status 200 whose body text the TLE_Parser accepts and the NORAD_CAT_ID of the resulting TLE_Record differs in integer value from the requested NORAD catalog number (a line 1 NORAD field `00005` has the integer value 5 and matches a request for 5), THEN THE TLE_Fetcher SHALL report an Engine_Error of category catalog-mismatch.
12. WHILE the TLE_Cache holds no entry for NORAD catalog number 25544, WHEN a caller requests 25544 from the TLE_Fetcher with the Mock_CelesTrak_Fetch as the Fetch_Function, THE TLE_Fetcher SHALL call the Mock_CelesTrak_Fetch exactly once, with a request URL that contains `CATNR=25544&FORMAT=tle` and does not contain `FORMAT=json`.
13. WHILE the TLE_Cache holds no entry for NORAD catalog number 25544, WHEN a caller requests 25544 from the TLE_Fetcher with the Mock_CelesTrak_Fetch as the Fetch_Function, THE TLE_Fetcher SHALL return exactly one TLE_Record whose fields equal the ISS values of Requirement 4, criterion 18, within the tolerances stated there, and whose raw line 1 and line 2 equal the two 69-character lines of the ISS Baseline_TLE_Snapshot without line terminators.
14. THE TLE_Fetcher SHALL send every request with a credentials mode other than `include`, because the CelesTrak_GP_Endpoint answers with `Access-Control-Allow-Origin: *` and browsers block such a response to a cross-origin request whose credentials mode is `include`.

### Requirement 4: TLE parsing and validation

**User Story:** As the zombieSatellite developer, I want three-line TLE text turned into a typed record with the section 4.2 fields, and every body that is not a valid TLE rejected, so that later specs show correct orbital elements and propagation runs only on valid TLEs.

#### Acceptance Criteria

1. WHEN the TLE_Parser accepts two TLE_Texts that differ only in using LF or CRLF line endings, THE TLE_Parser SHALL return TLE_Records with equal values in every field for the two TLE_Texts.
2. THE TLE_Parser SHALL remove trailing whitespace, including space, horizontal tab and carriage return characters, from every line of the TLE_Text before validating the lines and before storing line 1 and line 2 in the TLE_Record.
3. THE TLE_Parser SHALL set the object name of the TLE_Record to the object name line of criterion 20 with leading and trailing whitespace removed.
4. THE TLE_Parser SHALL extract fields at the C18 column positions (0-based, end-exclusive): from line 1, NORAD number [2:7], international designator [9:17], epoch year [18:20] and epoch day [20:32]; from line 2, NORAD number [2:7] (the same columns as in line 1), inclination [8:16], right ascension of the ascending node [17:25], eccentricity [26:33], argument of perigee [34:42], mean anomaly [43:51] and mean motion [52:63].
5. THE TLE_Parser SHALL set OBJECT_ID to line 1 columns [9:17] with surrounding spaces removed, which is the raw TLE form such as `98067A` and not the CelesTrak JSON form `1998-067A`.
6. THE TLE_Parser SHALL set ECCENTRICITY to the seven digits of the eccentricity field read with an implied leading decimal point (C09), so that `0007219` gives 0.0007219.
7. THE TLE_Parser SHALL compute EPOCH by C02 and formula 2.9.1: year = 2000 + yy when yy < 57 and 1900 + yy otherwise, and EPOCH = Date.UTC(year, 0, 0) + day × 86 400 000 ms.
8. THE TLE_Parser SHALL compute the semi-major axis as a = (μ / n²)^(1/3) with μ = 398600.4418 km³/s² and n = MEAN_MOTION × 2π / 86400 rad/s, using the raw TLE mean motion (C12, formula 2.9.7).
9. THE TLE_Parser SHALL compute the altitude as h = a − 6378.137 km, which is the semi-major-axis altitude and not the instantaneous altitude (C19).
10. WHERE the TLE_Record includes BSTAR, MEAN_MOTION_DOT, MEAN_MOTION_DDOT, ELEMENT_SET_NO, REV_AT_EPOCH, EPHEMERIS_TYPE or CLASSIFICATION_TYPE, THE TLE_Parser SHALL populate each included field with the value written in the corresponding line 1 or line 2 field of the TLE_Text, decoding the implied leading decimal point and the power-of-ten exponent of BSTAR and MEAN_MOTION_DDOT, instead of a placeholder value (C13–C16).

15. IF the NORAD numbers in line 1 and line 2 differ, THEN THE TLE_Parser SHALL report an Engine_Error of category invalid-tle.
16. IF satellite.js 6.0.2 `twoline2satrec`, called with line 1 and line 2, returns a Satrec with a non-zero error code or throws an exception, THEN THE TLE_Parser SHALL report an Engine_Error of category invalid-tle.
17. WHEN the TLE_Parser receives the body `No GP data found`, with or without a final LF or CRLF, THE TLE_Parser SHALL report an Engine_Error of category invalid-tle by the checks of criteria 11 to 16, independent of TLE checksum digits.

### Requirement 5: In-memory TLE cache

WHILE an In_Flight_Request for NORAD catalog number N exists, WHEN any further caller requests N, THE TLE_Fetcher SHALL give that caller the outcome of the In_Flight_Request without calling the Fetch_Function again: a TLE_Record equal in every field to the one returned to the caller that started the In_Flight_Request, or an Engine_Error with the same category and, for category http, the same HTTP status code.

### Requirement 10: Coarse scan and refinement accuracy

**User Story:** As a zombieSatellite user, I want pass start and end times within ±10 s and the peak elevation within ±0.5°, so that I start pointing my phone in time and the app does not repeat the reference project's 1-minute sampling error (P16: ISS pass 2 peak underestimated by 3.19°).

#### Acceptance Criteria

1. THE Pass_Predictor SHALL perform a Coarse_Scan with samples at the window start, at the window start plus k × 60 s for every integer k ≥ 1 for which that instant lies before the window end, and at the window end.
2. WHEN one of two adjacent Coarse_Scan samples is above Min_Elevation and the other sample is not, THE Pass_Predictor SHALL locate the crossing between the two samples by bisection until the bracket containing the crossing is at most 1 s wide.
3. WHEN the Pass_Predictor has identified a Pass that contains at least one Coarse_Scan sample above Min_Elevation, THE Pass_Predictor SHALL locate the Peak_Instant by iterated parabolic interpolation (successive parabolic interpolation safeguarded by golden-section steps, as in Brent's method) within the bracket from the Coarse_Scan sample immediately before to the Coarse_Scan sample immediately after the highest Coarse_Scan sample of the Pass, or within the bracket of criterion 9 or 10 at a window edge, until the Peak_Instant is bracketed within 0.1 s or less. (0.1 s, not 1 s: near the zenith the ISS Elevation changes by about 1° per second, so a 1 s bracket alone does not guarantee ±0.5°.)
4. WHEN the Pass_Predictor runs with the inputs of Requirement 13, criterion 1, THE Pass_Predictor SHALL report the second and the sixth Pass with a Maximum_Elevation within ±0.5° of 48.61° and of 58.59° respectively, the peak elevations of the Brute_Force_Passes of these two Passes (48.6098° from section 4.7; 58.5919° computed on 2026-11-14, not in the Reference_Document), which a single three-point parabola through the 60 s samples misses with 46.59° and 55.72°.
5. THE Pass_Predictor SHALL report the Rise_Instant of every Pass that is not start-truncated within ±10 s of the rise of the Brute_Force_Pass of that Pass.
6. THE Pass_Predictor SHALL report the Set_Instant of every Pass that is not end-truncated within ±10 s of the set of the Brute_Force_Pass of that Pass.
7. THE Pass_Predictor SHALL report the Maximum_Elevation of every Pass within ±0.5° of the peak elevation of the Brute_Force_Pass of that Pass.
8. THE Pass_Predictor SHALL report for every Pass a Maximum_Elevation greater than or equal to the Elevation of every Coarse_Scan sample whose instant lies in the closed interval [Rise_Instant, Set_Instant] of that Pass.
9. IF the Coarse_Scan sample around which criterion 3 places the bracket is the first Coarse_Scan sample, THEN THE Pass_Predictor SHALL use the bracket from the window start to the second Coarse_Scan sample.
10. IF the Coarse_Scan sample around which criterion 3 places the bracket is the last Coarse_Scan sample, THEN THE Pass_Predictor SHALL use the bracket from the second-to-last Coarse_Scan sample to the window end.
11. THE Pass_Predictor SHALL report each Rise_Instant and each Set_Instant that results from a crossing located by criterion 2 as an instant within the final bracket of that crossing, including the bracket ends.
12. IF a Pass has no Brute_Force_Pass (a pass shorter than 1 s between two 1 s samples) or has samples of two or more Brute_Force_Passes in its interval, THEN THE Test_Suite SHALL exempt that Pass from the comparisons of criteria 5 to 7.

### Requirement 11: Passes cut by the window edges

**User Story:** As the zombieSatellite developer, I want passes that are in progress at the window start or still running at the window end clipped to the window and flagged, so that later specs can tell a clipped boundary from a real rise or set.

#### Acceptance Criteria

1. IF the Propagator returns, for the Observer at the window start, an Elevation strictly greater than Min_Elevation, which excludes an Elevation equal to Min_Elevation and a propagation-failure result (Requirement 9, criterion 11), THEN THE Pass_Predictor SHALL report as the first Pass a Pass whose Rise_Instant is exactly the window start.
2. IF the Propagator returns, for the Observer at the window end, an Elevation strictly greater than Min_Elevation, which excludes an Elevation equal to Min_Elevation and a propagation-failure result (Requirement 9, criterion 11), THEN THE Pass_Predictor SHALL report as the last Pass a Pass whose Set_Instant is exactly the window end.
3. THE Pass_Predictor SHALL set Start_Truncated to true on the Pass that criterion 1 requires and to false on every other Pass, including every Pass whose Rise_Instant is located by bisection (Requirement 10, criterion 2, or Requirement 12, criterion 5).
4. THE Pass_Predictor SHALL set End_Truncated to true on the Pass that criterion 2 requires and to false on every other Pass, including every Pass whose Set_Instant is located by bisection (Requirement 10, criterion 2, or Requirement 12, criterion 6).
5. IF a Pass has Start_Truncated or End_Truncated true and its Elevation is greater at a window bound to which the Pass is clipped (the window start for Start_Truncated, the window end for End_Truncated) than at every other instant of the Pass, THEN THE Pass_Predictor SHALL report exactly that window bound as the Peak_Instant, even when the satellite reaches a higher Elevation before the window start or after the window end.
6. IF the Propagator returns an Elevation greater than Min_Elevation at every Coarse_Scan sample of the Search_Window (Requirement 10, criterion 1), THEN THE Pass_Predictor SHALL report exactly one Pass, with Rise_Instant exactly the window start, Set_Instant exactly the window end, and Start_Truncated and End_Truncated both true.
7. WHEN the Pass_Predictor runs for the ISS Baseline_TLE_Snapshot and the Reference_Observer with window start 2026-11-09T11:25:00Z, window duration 1 hour and Min_Elevation 0°, a window that starts after the 11:23:24Z peak of ISS pass 2 (section 4.7), THE Pass_Predictor SHALL report exactly one Pass, with Rise_Instant and Peak_Instant exactly 2026-11-09T11:25:00Z, Start_Truncated true, End_Truncated false and Set_Instant 2026-11-09T11:28:47Z ± 10 s.
8. WHEN the Pass_Predictor runs for the ISS Baseline_TLE_Snapshot and the Reference_Observer with window start 2026-11-09T10:21:00Z, window duration 1 hour and Min_Elevation 0°, a window that ends at 11:21:00Z, before the 11:23:24Z peak of ISS pass 2 (section 4.7), THE Pass_Predictor SHALL report exactly one Pass, with Rise_Instant 2026-11-09T11:18:05Z ± 10 s, Start_Truncated false, End_Truncated true, and Set_Instant and Peak_Instant exactly 2026-11-09T11:21:00Z.

WHEN the Pass_Predictor runs for the ZHIHUI TIANWANG-1 01A Baseline_TLE_Snapshot and the Reference_Observer with window start 2026-11-09T11:00:00Z, window duration 1 hour and Min_Elevation 0°, a window inside the section 4.6 pass 05:25–12:37 whose end is the section 4.3 instant with Elevation 14.6746°, THE Pass_Predictor SHALL report exactly one Pass, with Rise_Instant exactly 2026-11-09T11:00:00Z, Set_Instant exactly 2026-11-09T12:00:00Z, and Start_Truncated and End_Truncated both true.

### Requirement 12: Short passes near the threshold and pass-set stability

**User Story:** As a zombieSatellite user, I want short passes that peak just above the minimum elevation between two 60 s samples to be found, so that the pass list does not silently miss a pass.

#### Acceptance Criteria

1. THE Pass_Predictor SHALL refine every Coarse_Scan_Maximum whose Elevation is at or below Min_Elevation, whatever the difference between that Elevation and Min_Elevation, with the method and stopping rule of the peak refinement of Requirement 10, criterion 3, inside the bracket formed by the Coarse_Scan samples adjacent to that Coarse_Scan_Maximum, or by the window bound where that Coarse_Scan_Maximum is the first or last Coarse_Scan sample.
2. WHEN the refinement of criterion 1 returns an instant whose Elevation is greater than Min_Elevation, THE Pass_Predictor SHALL report a Pass whose Peak_Instant is that instant.
3. THE Pass_Predictor SHALL report, for every Min_Elevation from −90° to +90° and for each Brute_Force_Pass over the Search_Window whose peak elevation exceeds Min_Elevation by more than 0.1°, a Pass that overlaps the closed interval from the Brute_Force_Reference sample before that Brute_Force_Pass to its set, with the window start or the window end in place of a missing sample. (The 0.1° margin covers the elevation error that the 0.1 s peak bracket of Requirement 10, criterion 3 can leave near the zenith.)
4. WHEN the Pass_Predictor runs twice with the same TLE_Record, Observer, window duration and Min_Elevation, once with window start S and once with window start S + δ for an offset δ greater than −60 s and less than +60 s, THE Pass_Predictor SHALL return exactly one matching Pass in the other run for each Pass of either run that meets three conditions: its Rise_Instant and Set_Instant both lie inside the intersection of the two Search_Windows; it is neither start-truncated nor end-truncated; and it overlaps no start-truncated or end-truncated Pass of the other run. A Pass of the other run matches when its Rise_Instant and Set_Instant are each within ±10 s, and its Maximum_Elevation is within ±0.5°, of those of the Pass that meets the three conditions.
5. WHEN the Pass_Predictor reports a Pass by criterion 2, THE Pass_Predictor SHALL locate the Rise_Instant of that Pass by bisection between the Peak_Instant and the Coarse_Scan sample before the Coarse_Scan_Maximum, or the window start where the Coarse_Scan_Maximum is the first Coarse_Scan sample, until the bracket containing the crossing is at most 1 s wide.
6. WHEN the Pass_Predictor reports a Pass by criterion 2, THE Pass_Predictor SHALL locate the Set_Instant of that Pass by bisection between the Peak_Instant and the Coarse_Scan sample after the Coarse_Scan_Maximum, or the window end where the Coarse_Scan_Maximum is the last Coarse_Scan sample, until the bracket containing the crossing is at most 1 s wide.
7. IF the refinement of criterion 1 returns an instant whose Elevation is at or below Min_Elevation, THEN THE Pass_Predictor SHALL report no Pass for that Coarse_Scan_Maximum.
