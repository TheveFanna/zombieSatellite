### 2.9 核心公式与伪代码

#### 2.9.1 TLE epoch

```text
yy = int(line1[18:20])
year = (yy < 57) ? 2000+yy : 1900+yy
day  = float(line1[20:32])
t0   = Date.UTC(year, 0, 0) + day*86400000 ms
```

#### 2.9.2 视线角

```text
lookAngles(satrec, t, observer):
    (p_eci, v_eci) = SGP4(satrec, t)          # km, km/s, TEME
    θ = GMST(t)                                # rad
    p_ecf = Rz(-θ) * p_eci                     # km
    p_obs = WGS84toECF(observer)               # km
    Δ = p_ecf - p_obs
    (S,E,U) = ENU(observer.lat, observer.lon) * Δ
    r = sqrt(S² + E² + U²)
    el = asin(U / r)
    az = atan2(-E, S) + π                      # 0=北，顺时针
    if az >= 2π: az -= 2π                      # 推荐归一化；库边界可能返回 2π
    return (az, el, r)
```

#### 2.9.3 场景坐标

```text
toScene(az, el, R=20):
    x = R * cos(el) * sin(az)
    y = R * sin(el)
    z = -R * cos(el) * cos(az)
    return (x,y,z)

inverse(x,y,z):
    el = asin(y / R)
    az = atan2(x, -z) mod 2π
```

#### 2.9.4 校准旋转

```text
R_y(offset):
    x' =  x*cos(offset) + z*sin(offset)
    z' = -x*sin(offset) + z*cos(offset)
等效方位：az' = az - offset
```

#### 2.9.5 设备姿态到相机

```text
q_cam = quat(Euler(beta, alpha, -gamma, 'YXZ'))
        * Rx(-90°)
        * Rz(-screenOrientation)
forward = q_cam * (0,0,-1)
up      = q_cam * (0,1,0)
right   = q_cam * (1,0,0)

heading = atan2(forward.x, forward.y) mod 360   # 0=北，顺时针
pitch   = asin(forward.z)                       # 向上正
```

#### 2.9.6 HUD 制导

```text
f = normalize(camera.forward)
u = normalize(target - camera.position)
angle = acos(clamp(dot(f,u), -1, 1))
aligned = angle < 8°
behind  = dot(f,u) < 0
hudPos  = camera.position + 2*f
arrow.lookAt(target)
reticle.lookAt(camera.position)
```

#### 2.9.7 轨道高度

```text
n = MEAN_MOTION * 2π / 86400          # rad/s
a = (398600.4418 / n²)^(1/3)          # km
h = a - 6378.137                      # km
```

#### 2.9.8 过境预测

```text
passes = []
inPass = false
for t = t0; t < t0 + duration; t += 1 min:
    a = lookAngles(satrec, t, observer)
    visible = (a != null && a.el > 0)
    if visible and not inPass:
        inPass = true; start = t; maxEl = a.el
    else if visible and inPass:
        maxEl = max(maxEl, a.el)
    else if not visible and inPass:
        inPass = false; push(start, t, maxEl, (t-start)/60000)
if inPass:
    push(start, end, maxEl, (end-start)/60000)   # 窗口结束截断
```

## 3. 开发中遇到的坑与当时的处理方法

> 下列条目均可在当前代码、代码注释或提交记录中复核。标注“当前仍存在”的，表示不是历史问题，而是验收时应特别关注的遗留风险。

### P01 相机必须运行在安全上下文

- 现象：HTTP 下 `navigator.mediaDevices` 不存在或相机直接失败。
- 处理：进入 AR 先检查 `window.isSecureContext`；失败时明确提示“需要 HTTPS 或 localhost”；对 `NotAllowedError`、`NotFoundError` 分别给出中文错误。
- 验收：非安全上下文应显示错误而不是黑屏；localhost 或 HTTPS 下可获流。

### P02 相机画面黑屏，直到窗口尺寸变化才恢复

- 现象：视频已播放但首帧不显示，触发 resize 后才出现。
- 处理：`loadedmetadata` 后再 `play()`；在相机成功后立即执行一次“强制重绘”：把 video 的 transform 临时改为 `scale(1.0001)`，下一帧恢复 `none`，并派发 `window.resize`；分别在 0、200、500、1000 ms 重试。
- 验收：相机授权后 1 s 内应看到画面；旋转屏幕/改变窗口尺寸不应成为显示的必要条件。

### P03 子路径部署导致 API/静态资源 404

- 现象：部署在 `/sat-aware` 下，客户端仍请求 `/api/...`，或 manifest 图标路径错误。
- 处理：`next.config.ts` 设置 `basePath` 与 `NEXT_PUBLIC_BASE_PATH`；所有客户端 fetch、manifest `start_url`/icons 都拼接 `BASE_PATH`。
- 坑：`.env` 写 `BASE_PATH=""`，但配置使用 `process.env.BASE_PATH || "/sat-aware"`，空字符串仍是假值，实际仍为 `/sat-aware`；想部署到根路径不能只清空该变量，需要改配置。
- 验收：在 `/sat-aware/` 下所有 API 返回 JSON、静态资源 200；根路径部署需显式改为空 basePath。

### P04 iOS 姿态权限必须由用户手势触发

- 现象：自动请求 `DeviceOrientationEvent.requestPermission()` 被拒绝；或用户拒绝后一直停在加载页。
- 处理：增加 `waiting_permission` 状态和“点击授权传感器”按钮；在按钮事件中请求权限并同时尝试全屏；授权成功写 `localStorage['ar_permission_granted']`；提供错误重试。
- 坑：如果 `ar_permission_granted` 为 true，但 iOS 在非手势环境拒绝自动请求，`requestOrientation(true)` 的 catch 不设置错误，`orientation` 可能长期停在 `pending`，加载遮罩没有重试按钮。当前仍存在，验收时应清 localStorage 或刷新页面。
- 验收：首次进入必须出现授权按钮；授权后进入 AR；拒绝后显示错误并可重试。

### P05 航向“真北/磁北/相对北”不一致

- 现象：iOS `webkitCompassHeading`、Android `alpha`、`AbsoluteOrientationSensor` 的参考不一致；UI 航向与场景朝向可能不同步。
- 处理：场景统一由 `DeviceOrientationControls` 使用 `alpha/beta/gamma`；UI 另算航向；增加手动 ±5° 世界旋转校准；提示画“8”字校准罗盘。
- 坑：`DeviceOrientationControls` 只订阅 `deviceorientation`，不使用 `deviceorientationabsolute`/传感器四元数；某些 Android/iOS 的 `deviceorientation.alpha` 可能是相对值，场景会随设备启动方向漂移，手动常量偏移无法修复动态漂移。当前仍存在。
- 验收：在同一设备上，UI 航向与场景北向应在 ±5° 内；若不一致，先确认 `alpha` 是否 absolute，再做手动校准。

### P06 世界旋转后 HUD 箭头指向错误

- 现象：为了让罗盘/卫星对齐而旋转世界组后，卫星标记和轨迹转了，但 HUD 箭头仍在未旋转空间，指向偏了一个偏移角。
- 处理：HUD 目标位置用 `applyAxisAngle(Y, calibrationRotation)` 把卫星场景坐标变换到未旋转的相机空间；世界组只包卫星、轨迹、罗盘。
- 验收：校准 +10° 后，箭头与卫星标记应保持同一方向；准星在目标进入 8° 内出现。

### P07 目标在身后时箭头“看起来”仍指前方

- 现象：HUD 固定在相机前方，目标在身后时箭头仍显示在屏幕中央附近，用户不知道要转身。
- 处理：用 `dot(forward,target)<0` 判身后；箭头变红、脉冲加快（角速度 10 vs 5）；前方为青色。
- 坑：箭头仍位于 HUD 前方，不会自动指向“转身方向”；这是 UX 限制，不是坐标错误。
- 验收：目标在身后时颜色为红、脉冲更快；转身后恢复青色。

### P08 HUD 被场景物体遮挡

- 现象：箭头/准星被卫星标记或轨迹挡住。
- 处理：HUD 材质 `depthTest=false`，部分使用 additive blending；HUD 固定在相机前 2 单位。
- 验收：箭头/准星始终可见；卫星标记可被 HUD 覆盖。

### P09 真实斜距会导致 near/far 和尺度问题

- 现象：卫星斜距几百到几万 km，直接用作场景半径会超出相机 far 或让标记小到不可见。
- 处理：所有卫星/轨迹统一使用 `R=20` 的场景球面，只保留方位/仰角；标记尺寸固定。
- 坑：不同高度的卫星在画面上没有距离差异；轨迹是“方向轨迹”而不是真实比例轨道。
- 验收：低轨和高轨卫星都应落在同一半径球面上；UI 仍显示真实斜距（若展示）。

### P10 CelesTrak ID 搜索的 JSON/TLE 格式不匹配（当前缺陷）

- 现象：`id` 分支请求 `FORMAT=json`，但后续按 TLE 三行文本解析；实际响应是一行 JSON，循环直接结束，返回空数组。
- 影响：按 NORAD ID 精确搜索失败；首次默认卫星 `id=59705` 也无法自动加载。
- 当前处理：无（代码仍为 JSON 请求 + TLE 解析）。
- 建议修复：ID 分支改用 `FORMAT=tle`，或对 JSON 响应走 `JSON.parse` 并映射字段；两者只能选其一，不能混用。
- 验收：`?id=25544` 应返回 ISS 一条记录；当前预期为 `[]`（HTTP 200），这是已知失败样例。

### P11 CelesTrak 的“200 但无数据”响应

- 现象：CelesTrak 可能返回 HTTP 200，正文是 `No GP data found` 或 `No records found`，而不是 404。
- 处理：先检查正文关键字，再检查状态码；都按 404 处理。
- 坑：如果返回 HTML 错误页，关键字不匹配，解析可能得到空数组并返回 200 `[]`；前端会显示“无搜索结果”而不是“服务异常”。
- 验收：无数据关键字必须返回 404；HTML 错误页应返回 500 或明确错误。

### P13 TLE 解析字段只是“展示元数据”

- 现象：`parseTLE` 把 `EPHEMERIS_TYPE`、`CLASSIFICATION_TYPE`、`ELEMENT_SET_NO`、`REV_AT_EPOCH`、`BSTAR`、`MEAN_MOTION_DOT`、`MEAN_MOTION_DDOT` 设为固定占位值（0/U/999 等），而不是真实解析。
- 处理：传播始终使用原始 `TLE_LINE1`/`TLE_LINE2` 交给 satellite.js，不依赖这些占位字段。
- 坑：若后续用这些字段做阻力/寿命分析，会得到错误结果；UI 不应展示它们为真实值。
- 验收：传播结果与原始 TLE 一致；占位字段不得用于计算。

### P16 1 分钟过境采样的误差

- 现象：过境开始/结束/最大仰角都取 1 min 网格；最大仰角可能明显低于真实最大值。
- 处理：接受 1 min 分辨率；卡片和 API 使用同一算法；没有插值。
- 实测：ISS 某次过境的 1 min 结果为 11:19–11:29、最大 45.42°；1 s 参考为 11:18:05 升起、11:23:24 最大 48.61°、11:28:47 落下。最大仰角低估约 3.19°，边界差约 13–55 s。
- 坑：如果过境在窗口结束时仍可见，`endTime` 被截断为窗口结束，时长偏短；查询时已经在地平线上的过境，`startTime` 被截断为查询时刻。
- 验收：同一 TLE/观测站，1 min 算法结果应与本文样例一致；不要用 1 s 参考去要求 0.1° 精度。

### P17 客户端过境计算可能阻塞 UI

- 现象：每张卡片在浏览器里对 24 h 做 1440 次传播；卫星多时首屏卡顿。
- 处理：用 `setTimeout(100)` 把计算推迟到渲染之后；完整过境 API 已实现可下沉到服务端；但当前页面未挂载 `PassPredictions`，卡片仍走客户端。
- 坑：卫星数量多时仍是 O(卫星数×1440) 的主线程计算；没有 Web Worker、缓存或取消机制。
- 验收：5 颗卫星首屏不应出现明显长任务；如出现，优先把卡片预测改为服务端/Worker。

### P19 相机 FOV 与视频画面不匹配

- 现象：卫星标记在画面中的位置与真实 Camera 画面有偏移，尤其横屏/广角/长焦。
- 处理：Canvas 固定 `fov=75°` 垂直视场；视频用 CSS `object-cover` 铺满；没有读取摄像头内参/实际 FOV。
- 坑：`object-cover` 会裁剪，实际水平/垂直 FOV 随设备宽高比变化；固定 75° 无法覆盖所有设备。当前仍存在。
- 验收：同一设备上卫星应在正确方位附近；跨设备绝对角度对齐不能作为硬指标，除非增加 FOV 标定。

### P20 设备姿态输入源不统一

- 现象：场景用 `deviceorientation`，UI 可能用 `webkitCompassHeading`、`deviceorientationabsolute`、`AbsoluteOrientationSensor`；三者参考系/刷新率不同。
- 处理：场景只依赖 `DeviceOrientationControls`；其他源只做 UI 展示；增加手动校准。
- 坑：iOS 的 `alpha` 可能是相对值，`webkitCompassHeading` 才是罗盘；但场景没有用后者，导致 UI 航向与场景方向不一致。`AbsoluteOrientationSensor` 的 `referenceFrame:'device'` 与屏幕方向的关系也未参与场景。
- 验收：不要用 UI 航向直接断言场景朝向；以画面中已知地标/罗盘 N 标签做现场校验。

### P21 `alpha=0`、空值和屏幕方向导致的跳变

- 现象：传感器短暂返回 `null` 或 `alpha=0` 时，three-stdlib 用 `device.alpha ? ... : 0` 处理，可能把瞬间空值当 0，画面跳一下。
- 处理：当前没有额外滤波/保持上一帧；依赖浏览器事件稳定性。
- 坑：快速旋转、后台切换、权限变化时会出现跳变；没有低通滤波或四元数插值。
- 验收：快速转动后画面应稳定；若跳变明显，需要加姿态滤波。

### P22 校准偏移的符号与负数取模

- 现象：`headingOffset` 正方向是“世界绕 +Y 旋转”，不是“设备航向加偏移”；用户按 +5° 时目标有效方位反而减小 5°。
- 处理：UI 用“↺ -5° / ↻ +5°”让用户试；值写入 localStorage；世界组和 HUD 目标同步旋转。
- 坑：`(offset+delta)%360` 对负数不归一到 0–360，可能显示 -5°；`parseFloat` 读入非法值会得到 NaN，未校验。
- 验收：+10° 后，正东目标（az=90°）的场景有效方位变为 80°；见第 4 节合成样例。

### P23 占位卫星/空 TLE 也会被判为“就绪”

- 现象：`satelliteData` 只在 NORAD=0 且名称“加载中...”时判 pending；如果真实卫星对象存在但 TLE 为空/损坏，仍会 `success`。
- 处理：Scene 内 `getSatRec` 失败时返回 null，卫星标记不显示；加载遮罩不会提示。
- 坑：用户可能进入 AR 后看不到卫星，也没有错误信息。当前仍存在。
- 验收：空 TLE 应显示明确错误或停留在加载页；不能只显示空白 AR。

### P25 PWA 图标缺失与部署细节

- 现象：`manifest.ts` 引用 `/icon-192.png`、`/icon-512.png`，但 `public/` 当前没有这两个文件。
- 处理：manifest 逻辑正确，但资源未提供；安装到主屏可能没有图标或 404。
- 验收：`/sat-aware/manifest.webmanifest` 可访问；两个图标 URL 应 200。

### P26 没有自动化测试

- 现象：仓库没有 test 脚本/测试目录；回归依赖手工。
- 处理：本文第 4 节给出一组固定 TLE、固定 UTC、固定观测站的数值基线；建议把它们固化为单元测试（视线角、场景坐标、过境、TLE 解析、ID 搜索格式）。
- 验收：相同依赖版本下，数值应在给定容差内复现。

### 4.5 设备姿态到相机朝向基线

按 `q_cam = Euler(beta, alpha, -gamma, 'YXZ') * Rx(-90°) * Rz(-screenOrientation)`，屏幕方向 0°：

| alpha | beta | gamma | 相机前向 (x,y,z) | 含义 |
|---|---|---|---|---|
| 0° | 90° | 0° | (0, 0, -1) | 北 |
| 90° | 90° | 0° | (-1, 0, 0) | 西 |
| 180° | 90° | 0° | (0, 0, 1) | 南 |
| 270° | 90° | 0° | (1, 0, 0) | 东 |
| 0° | 0° | 0° | (0, -1, 0) | 垂直向下（手机平放，屏幕朝上） |

配套 UI 约定：

- `alpha=0` 时 `360-alpha` 得到 360.0，而不是 0.0；验收时允许 0/360 等价。
- `alpha=90` 显示航向 270°（西）；`alpha=270` 显示 90°（东）。
- `beta=90` 时 UI 俯仰应为 0°；`beta=0` 时俯仰为 -90°（向下）。

### 4.10 验收建议

1. **单元级**：固定 4.2 的 TLE、4.3 的时刻和观测站，断言 ECI/ECF、方位/仰角/斜距、场景坐标、海拔高度。容差按 4.1。
2. **过境级**：固定 `t0=2026-11-09T00:00:00Z`，断言 4.6 的段数、起止、最大仰角；允许 ±1 min。
3. **姿态级**：用 4.5 的表驱动测试 `alpha/beta/gamma` 到相机前向的映射；特别验证 0/360 等价。
4. **校准级**：断言 `az=90°, offset=+10°` 得到有效 80° 和场景 (19.696155, 0, -3.472964)。
5. **接口级**：名称搜索正向；ID 搜索当前负向（P10），修复后转为正向。
6. **现场级**：相机画面与卫星标记的绝对对齐受 FOV/磁北/设备差异影响，建议用已知地标或罗盘 N 标签做人工验收，不把跨设备绝对角度作为硬性自动化指标。
